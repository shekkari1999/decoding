Speculative Sampling: From Intuition to a Correct Implementation

How a small language model can help a larger model generate several tokens per expensive verification pass—without changing the larger model's sampling distribution.

Start With the Basic Idea

Language models generate text autoregressively: one token becomes part of the context used to predict the next token. A conventional decoder asks the same large model for one new token at every step.

prompt → large model → token 1
prompt + token 1 → large model → token 2
prompt + token 1 + token 2 → large model → token 3

Speculative sampling asks whether a cheaper model can guess several of those future tokens first. The cheap model is the draft model. The model whose behavior we must preserve is the target model.

Suppose the current prefix is:

The capital of France is

The draft proposes four tokens:

Paris . It is

The target checks that entire block. If it accepts multiple guesses, we advance by multiple tokens after one target verification pass. If a guess is rejected, the target-corrected output is committed and the process starts another round.

The draft does not replace or override the target. It only proposes work that the target may accept. The final algorithm must sample from the target distribution exactly.

Why This Can Be Faster

During batch-one decoding, a large model repeatedly reads its weights from GPU memory while doing relatively little work for each weight. This makes decoding commonly memory-bandwidth-bound rather than compute-bound.

A target model still performs substantial computation when it verifies a block. The advantage is that processing several positions together gives the GPU a wider operation, and one target pass may produce several useful tokens.

speedup requires: saved target steps > draft work + verification overhead

This immediately reveals the main tradeoff. A smaller draft is cheaper, but it may disagree more often with the target. A larger draft may achieve higher acceptance, but its proposal cost is higher. The proposal length k has the same tension: longer blocks create more upside when accepted and more wasted work after an early rejection.

Speculative decoding versus speculative sampling

The general technique is often called speculative decoding. Greedy decoding can verify whether draft choices agree with the target's deterministic choices. Speculative sampling is the stochastic version: it must preserve the complete probability distribution of target-only sampling, not merely produce plausible text.

One Speculative Round

1. DraftSample up to k candidate tokens.
2. VerifyRun the proposed block through the target.
3. DecideAccept left to right until the first rejection.
4. CommitAdd accepted tokens plus a correction or bonus.

Consider a round in which the draft proposes four tokens but the target rejects the third:

x₁ accepted x₂ accepted x₃ rejected x₄ discarded y correction

We commit x₁, x₂, y. We cannot continue checking x₄, because the draft generated it under a prefix containing x₃. Once x₃ is rejected, that conditioning history no longer exists.

If all four proposals pass, we commit all four and may sample one additional bonus token from the target's next-token distribution. That gives a maximum of k + 1 committed tokens in a full-acceptance round.

The notation is simple:

q = draft probabilities    p = target probabilities    x = proposed token

The Exact Sampling Rule

The draft samples a token x from q. We then ask how much probability that same token receives under p.

acceptance probability α(x) = min(1, p(x) / q(x))

There are two intuitive cases:

  • If p(x) ≥ q(x), the target gives the token at least as much probability as the draft. Accept it every time.
  • If p(x) < q(x), the draft proposes the token too often relative to the target. Accept it only with probability p(x)/q(x).

In code, we draw a uniform random number u and compare it with the acceptance probability:

# q(x): probability assigned by the draft to its proposed token.
q_of_draft = draft_chosen_probs[position]

# p(x): probability assigned by the target to that same token.
p_of_draft = target_probs_for_draft[0, position].item()

# Clamp the denominator only to protect against division by zero.
acceptance_probability = min(1.0, p_of_draft / max(q_of_draft, 1e-12))

# The proposal passes when a uniform draw falls below the acceptance probability.
uniform_draw = torch.rand((), device=draft_ids.device).item()
is_accepted = uniform_draw < acceptance_probability

Why rejection needs a correction distribution

Rejection cannot mean “sample normally from p.” Some target probability mass has already been represented through accepted draft proposals. Sampling from p again would double-count it.

The accepted branch contributes min(p, q). The remaining mass needed to recover the target distribution is therefore:

residual(x) = max(p(x) − q(x), 0)

At the first rejection, we normalize that residual and draw the correction token from it:

# Keep only target probability mass not already represented by the draft.
residual = (target_probs[0, position] - draft_probs_history[position]).clamp_min(0)

# Convert the remaining mass back into a probability distribution.
correction_probs = residual / residual.sum()

# This token replaces the rejected proposal.
correction = torch.multinomial(correction_probs, num_samples=1)
Why save the full q distribution? The acceptance ratio needs only q(x) for the selected proposal. The residual needs p(t)-q(t) for every possible token t in the vocabulary.

A small numerical example

Imagine a three-token vocabulary. The draft and target distributions are:

Tokenq draftp targetmax(p-q, 0)
A0.600.300.00
B0.300.400.10
C0.100.300.20

If the draft proposes A, it is accepted with probability 0.30/0.60 = 0.5. If rejected, the residual contains no A mass. After normalization, the correction chooses B with probability 1/3 and C with probability 2/3. The acceptance and correction branches together reconstruct the target probabilities.

The Subtle Part: Aligning Causal Logits

A causal model's output at position i predicts the token at position i+1. Consequently, target verification logits do not line up with proposal IDs at identical indices.

Let the accepted prefix be s, and let the draft propose x₁, x₂, x₃, x₄:

  • The final target prefill logit after s predicts x₁.
  • Verification position 0 consumes x₁ and predicts x₂.
  • Verification position 1 consumes x₂ and predicts x₃.
  • Verification position 2 consumes x₃ and predicts x₄.
  • Verification position 3 predicts the optional bonus token.
# The prefill's final logit verifies proposal 1.
# The first k-1 verification logits verify proposals 2 through k.
target_logits_for_draft = torch.cat(
    [
        target_prefill.logits[:, -1:, :],
        target_verification.logits[:, : k - 1, :],
    ],
    dim=1,
)
Classic off-by-one bug: comparing draft_ids[:, i] with target_verification.logits[:, i]. The latter predicts the token after proposal i, not proposal i itself.

Building the Algorithm in Stages

Stage 1: Validate tokenizer compatibility

The two models communicate using token IDs. Equal vocabulary sizes are not sufficient; the same integer must identify the same token in both tokenizers.

# Compare the complete token-to-ID mappings, not only their sizes.
assert target_tokenizer.get_vocab() == draft_tokenizer.get_vocab()

# Restrict both output heads to the real shared vocabulary.
spec_tokenizer = target_tokenizer
shared_vocab_size = len(spec_tokenizer)

Stage 2: Prefill both models

Each model processes the accepted prefix once. The returned KV caches prevent us from recomputing attention state for the same prefix during every new-token step.

# prefix_ids has shape [1, prefix_length].
target_prefill = target_model(input_ids=prefix_ids, use_cache=True)
target_cache = target_prefill.past_key_values

draft_output = draft_model(input_ids=prefix_ids, use_cache=True)
draft_cache = draft_output.past_key_values

Stage 3: Let the draft propose k tokens

The draft is still autoregressive. It proposes one token, feeds it back, and then proposes the next. For every position, we retain the selected token, its selected probability, and the full distribution.

draft_tokens = []
draft_chosen_probs = []
draft_prob_distributions = []

for proposal_index in range(k):
    # Convert the latest draft logits into q.
    draft_logits = draft_output.logits[:, -1, :shared_vocab_size]
    draft_probs = draft_logits.float().softmax(dim=-1)
    draft_prob_distributions.append(draft_probs[0])

    # Sample x from q and remember q(x).
    proposed_token = torch.multinomial(draft_probs, num_samples=1)
    draft_tokens.append(proposed_token)
    draft_chosen_probs.append(
        draft_probs.gather(-1, proposed_token).item()
    )

    # Feed the proposal back unless it is the last one in this block.
    if proposal_index < k - 1:
        draft_output = draft_model(
            input_ids=proposed_token,
            past_key_values=draft_cache,
            use_cache=True,
        )
        draft_cache = draft_output.past_key_values

draft_ids = torch.cat(draft_tokens, dim=1)
draft_probs_history = torch.stack(draft_prob_distributions, dim=0)

Stage 4: Verify the block with the target

# The cached target state already contains the accepted prefix.
target_verification = target_model(
    input_ids=draft_ids,
    past_key_values=target_cache,
    use_cache=True,
)

This is the operation that creates the opportunity for speedup. The expensive target evaluates the proposal positions together instead of requiring a separate target call before every token.

Stage 5: Scan left to right

For each position, gather p(x) and compare a uniform draw with min(1, p(x)/q(x)). Increment accepted only for the consecutive prefix. Break immediately at the first rejection.

accepted = 0

for position in range(k):
    q_x = draft_chosen_probs[position]
    p_x = target_probs_for_draft[0, position].item()
    alpha = min(1.0, p_x / max(q_x, 1e-12))

    if torch.rand((), device=draft_ids.device).item() >= alpha:
        # Build and sample the residual correction here.
        break

    accepted += 1

Stage 6: Choose the continuation

if accepted < k:
    # Commit the accepted prefix and one correction token.
    continuation = torch.cat(
        [draft_ids[:, :accepted], correction], dim=1
    )
else:
    # Every proposal passed; the target can provide one bonus token.
    bonus_logits = target_verification.logits[:, -1, :shared_vocab_size]
    bonus_probs = bonus_logits.float().softmax(dim=-1)
    bonus_token = torch.multinomial(bonus_probs, num_samples=1)
    continuation = torch.cat([draft_ids, bonus_token], dim=1)

KV Caches Are Algorithmic State

A KV cache stores the attention keys and values for tokens already processed by a model. It is not merely a performance option here. Because speculation temporarily processes tokens that may be discarded, cache state becomes part of the algorithm's correctness.

target cache length = draft cache length = committed sequence length

That invariant should hold at the end of every round. During the round, however, the two caches advance differently.

Rolling back the target

The target verification call processes all k proposals. If only accepted proposals survive, remove the rejected proposal and everything after it:

tokens_to_remove = k - accepted
verified_target_cache.crop(-tokens_to_remove)

Then feed the correction token once, so the cache includes the complete committed continuation.

The draft cache is one proposal behind

In our loop, the draft's final proposal was sampled from the latest logits but was not fed back into the model. Therefore, after proposing k tokens, its cache contains only k-1 new proposal entries.

After a rejection, its removal count is:

draft tokens to remove = (k − 1) − accepted

After full acceptance, the draft must process both its previously unprocessed final proposal and the target's bonus token. This off-by-one is easy to miss because the draft has sampled k tokens even though its cache has consumed only k-1.

Version-specific detail: in the Transformers version used for this implementation, DynamicCache.crop(-n) removes n entries, while a positive argument specifies an absolute final length. Cache APIs should be checked against the installed version.

Details That Determine Correctness

EOS and minimum output length

If EOS is disallowed before min_new_tokens, it must be masked in both p and q. Otherwise, the acceptance ratio compares two distributions with different supports. Maximum length also controls whether there is room to emit a bonus token.

Numerical stability

Compute softmax probabilities in FP32 even when model weights use BF16. Clamp the residual at zero to remove tiny negative values caused by floating-point error. If its total mass is numerically zero, use a safe fallback such as the target distribution.

Deterministic debugging

A speculative sampler uses randomness for draft sampling, acceptance draws, correction sampling, and bonus sampling. A dedicated seeded torch.Generator makes a failing path reproducible without claiming that one deterministic run proves distributional correctness.

Useful runtime assertions

# Both models must end the round at the same committed sequence length.
assert target_cache.get_seq_length() == committed_length
assert draft_cache.get_seq_length() == committed_length

# Probabilities should be finite and normalized.
assert torch.isfinite(target_probs).all()
assert torch.isfinite(draft_probs_history).all()
assert torch.allclose(target_probs.sum(-1), torch.ones_like(target_probs.sum(-1)))

Beyond runtime assertions, exactness should be tested statistically: sample many outputs with target-only sampling and speculative sampling under the same policy, then compare empirical token frequencies or use an appropriate goodness-of-fit test.

Correct Does Not Automatically Mean Fast

The first educational implementation used Qwen2.5-7B as the target and Qwen2.5-0.5B as the draft on an NVIDIA L4. The saved notebook measurements were:

ConfigurationThroughputAdditional result
Target-only 7B17.0 tokens/sGreedy baseline
Draft-only 0.5B53.5 tokens/sGreedy baseline
Educational speculative sampler12.1 tokens/s32.3% acceptance, k=3

The speculative implementation was slower than the target-only baseline. That is a useful result, not a failure to hide.

  • At 32.3% acceptance, much of the draft work was discarded.
  • Rejections required correction work and cache repair.
  • Python loops and .item() calls introduced synchronization overhead.
  • The comparison mixed an educational stochastic implementation with a highly optimized generation path.
  • A production engine can fuse operations and schedule model work differently.
The right conclusion: speculative sampling has a sound algorithmic opportunity, but speedup depends on draft cost, acceptance rate, proposal length, hardware, workload, and engine implementation.

How to benchmark it fairly

Hold the following constant between target-only and speculative runs:

  • Prompts, output lengths, batch size, and concurrency
  • Temperature, top-p, top-k, EOS rules, and random-seed policy
  • Precision, quantization, model revisions, and tensor parallelism
  • Warmup procedure and timing boundaries

Measure more than tokens per second. Record acceptance rate, accepted tokens per round, target passes per generated token, draft passes, rejection position, latency distribution, and peak memory. Sweep several proposal lengths rather than selecting one favorable value.

Scaling the Experiment

The next experiment uses Llama 3.1 70B Instruct as the target and Llama 3.1 8B Instruct as the draft. Their token-to-ID mappings were checked for equality before loading the complete weights.

BF16 weights require roughly 140 GB for the target and 16 GB for the draft. Two approximately 96 GB GPUs provide enough aggregate capacity, but aggregate memory is not sufficient evidence that the layout will run. Tensor-parallel balance, KV caches, temporary workspaces, and inter-GPU communication also matter.

  1. Load and test the 70B target alone.
  2. Record its device placement and peak memory per GPU.
  3. Test the 8B draft independently.
  4. Load both models and inspect remaining headroom.
  5. Run one speculative round with cache assertions.
  6. Exercise rejection, full acceptance, EOS, and length-boundary paths.
  7. Only then run matched benchmarks.

What I Learned

  1. The draft proposes; the target remains authoritative. Speculation must preserve the target distribution.
  2. Exact sampling requires both acceptance and correction. The rules are min(1, p/q) and normalized max(p-q, 0).
  3. Causal logits are shifted. The prefill output verifies the first proposal; later verification outputs align with later proposals.
  4. Acceptance stops at the first rejection. All subsequent draft tokens depend on a prefix that has become invalid.
  5. KV caches are mutable algorithmic state. Both caches must end every round at exactly the committed sequence.
  6. Sampling a token is not the same as caching it. This creates the draft cache's k-1 off-by-one.
  7. Tokenizer compatibility means mapping equality. Equal vocabulary sizes alone prove little.
  8. Correctness and performance are separate experiments. A readable reference implementation is not a production serving engine.
  9. Acceptance rate is not the only metric. It must be interpreted together with draft cost, target passes, and orchestration overhead.
  10. A negative benchmark is still evidence. It identifies what must improve instead of turning a theoretical speedup into an unsupported claim.

Speculative sampling is often summarized as “use a small model to make a large model faster.” The implementation reveals a more precise idea: borrow proposals from a cheap distribution, use rejection sampling to preserve an expensive distribution, and carefully roll back every piece of computational state that was created by guesses we did not commit.
